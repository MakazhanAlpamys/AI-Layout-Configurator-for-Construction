## Fixed unit defect

The root cause of VQ-01…VQ-04 was shared: in `static/style.css` line widths
were set together with `vector-effect: non-scaling-stroke`, i.e. interpreted as
**screen pixels**, while text sizes and marker radii were in
**user units (mm)**. The values, meanwhile, had been chosen as if it were the
other way round. With a `viewBox` of 54000×30000 and an SVG width of 894 CSS px the scale is
60.4 mm per pixel.

| Element | Before | After |
| --- | --- | --- |
| Flow corridor | `.flow-route` 120 px ≈ 7248 mm band over the plan | `.flow-corridor` at the declared width: measured 1800 mm (29.8 px) and 1200 mm (19.9 px) |
| Route centerline | absent | `.flow-route` 2 px hairline over the corridor |
| Structural grid line | 16 px ≈ 966 mm | 1 px |
| Room label | `font-size: 180px` in user units → 2.98 px | `calc(var(--u) * 13px)` → 13.0 px |
| Issue marker | `r = 280` mm → 4.64 px | `px(7)` → 7.0 px |

Mechanics of the fix:

- `drawPlan` computes `projectionUnit` — the number of user units per one
  rendered CSS pixel — and publishes it as the CSS variable `--u` on `#plan`;
- CSS sets text sizes and label outlines as `calc(var(--u) * Npx)`;
- all non-line offsets, marker radii and the resize handle size are computed via
  the local helper `px()`;
- the reference grid step is raised to at least 9 px, otherwise a 100 mm step merges
  into a solid fill on a facility of this size;
- the plan is redrawn when the window is resized, because the unit depends
  on the rendered size;
- room labels are shrunk to fit the room width and removed if they cannot fit
  legibly; the area is removed together with the name;
- the flow label offset was also in millimetres (260 mm ≈ 4 px), which caused
  routes in a shared corridor to be printed on top of each other; now the offset is in screen units, and
  the label unfolds from its anchor towards the side where there is room.

The regression is covered by the tests `tests/test_ui.py::PlanProjectionUnitTests`: they
forbid a `stroke-width` greater than 6 px in rules with `non-scaling-stroke`, require
`var(--u)` in plan text sizes and require the client to publish the unit.

## Issue status consistency — fixed 2026-09-06

`VQ-05` and `VQ-06` were a single discrepancy: the plan, the list and the counter interpreted
closing an issue differently. An issue closed in the session dropped out of `openIssues`,
and the resolved-marker loop drew only topics with `record_type === "bcf"`, so
the finding disappeared from the plan entirely. Meanwhile the header badge counted all issues
regardless of status.

Fixed:

- the server snapshot returns `issue_counts` (`open`, `resolved`, `total`), computed
  from managed statuses; the plan, the list and the badge read the same source;
- a resolved marker is drawn also for current findings closed in the session, not only
  for BCF topics that have disappeared; the coordinate is taken from the viewpoint, or, if
  there is none, from the equipment or the midpoint of the route;
- `validation.ok` intentionally remains a deterministic verdict: closing an
  issue in the workflow does not make the geometry valid, so the badge shows
  `7 open · 1 resolved`, not `VALID`.

Verified in the browser on the conflict-fixture: before the action the badge shows `8 issue(s)`,
10 open markers, 0 resolved; after resolve — badge `7 open · 1 resolved`,
9 open markers and 1 resolved marker, and the panel shows the same numbers. Reopen
restores the original values. The regression is held by
`tests/test_ui.py::IssueStatusConsistencyTests`.
